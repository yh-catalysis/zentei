## 1. このドキュメントの目的

前提と判断は、人が手で書かずに溜める。このドキュメントは、何をどの順に読み、書かれていないことをどう扱い、抜き出した結果をどう確かめるかを決める。

記録の形は [01_Data_Model_Decision.md](01_Data_Model_Decision.md) で決めている。

---

## 2. 決定事項サマリ

| 論点 | 決定 |
| --- | --- |
| 読むもの | **エージェントのメモリと意思決定ドキュメントを先に読む。** 会話の履歴は、足りない分を補うために後で読む（[§3](#3-読むものと順番)） |
| 動かし方 | **利用者がコマンドを実行したときにまとめて読む。** 会話のたびには抽出しない（[§3](#3-読むものと順番)） |
| 増えた分の見分け方 | **文書の内容のハッシュを控え、変わった文書だけを読む**（[§4](#4-増えた分の見分け方)） |
| 取り込む判断 | **理由が書かれている判断だけ**（[§5](#5-取り込む範囲)） |
| 依存の強さ | **理由が1つだけならその理由を `critical` に固定する。** それ以外は文書に書かれているときだけ `critical`（[§6](#6-書かれていないことの扱い)） |
| 崩れる条件 | **前提の反対がはっきりしていれば書く。数量の境目は作らない**（[§6](#6-書かれていないことの扱い)） |
| 利用者への質問 | **記録どうしの食い違いと、数量の境目だけを溜める。** 強さは、前提が崩れた時点でその判断について聞く（[§6](#6-書かれていないことの扱い)） |
| 重複の避け方 | **同じリポジトリの記録と共通の前提を、抽出するモデルに渡して ID で参照させる**（[§7](#7-重複の避け方)） |
| モデルと検証 | **小さいモデルに決まった形で出力させ、文書1本の出力をまとめて検証する。** 誤りは1回だけ戻して出し直させる（[§8](#8-モデルと検証)） |

---

## 3. 読むものと順番

入口は3つある。

| 入口 | 性質 |
| --- | --- |
| 意思決定ドキュメント | 判断、理由、却下した案がまとまっている。1本に複数の判断がある |
| エージェントのメモリ | 利用者の指示や、作業で確かめた事実が、1件ずつ短く書かれている。日付が残っていることが多い |
| 会話の履歴 | 量が多く、利用者の発言はそのごく一部である。発言は直前の返答と対にしないと意味が取れない |

意思決定ドキュメントとメモリを先に読む。どちらもすでに整理された文章で、少ない量から正確に取れる。会話の履歴は、文書になっていない前提（利用者がうろ覚えで述べた事実など）を補うために、その後で読む。

会話のたびに抽出する方法は採らない。会話の終わりは作業の報告で終わることが多く、前提が述べられるのは途中である。会話ごとに抽出すると、毎回費用がかかるわりに取れるものが少ない。利用者がコマンドを実行したときに、増えた分をまとめて読む。

---

## 4. 増えた分の見分け方

文書ごとに、内容のハッシュを控える。控えと同じ文書は読まない。内容が変わった文書は読み直す。

読み直しでは、既存の記録を渡したうえで、新しく増えた前提と判断だけを足す。文書から消えた記述に対応する記録は、自動では消さない。消えた理由が「崩れた」のか「書き直した」のかを、文書だけからは決められないためである。

控えはマシンごとのファイルに置き、記録と同じ場所で同期する。別のマシンが読んだ文書を、もう一度読まずに済む。

---

## 5. 取り込む範囲

理由が書かれている判断だけを取り込む。画面の細かい仕様の列挙、作業の記録、手順は取り込まない。前提を持たない判断は、どの前提が崩れても見直しを促されないので、記録しても照会の役に立たない。

前提の日付は次のように決める。

| 文書の書き方 | 確かめた日 |
| --- | --- |
| 確かめた事実として書いている | 文書の日付 |
| 「たしか」「はず」「見込み」と書いている | 空（未確認として扱う） |

文書の日付は、メモリなら項目の更新日、意思決定ドキュメントなら、そのファイルが Git に足された日とする。文書の中に決めた日があれば、判断の日付にはそちらを使う。

---

## 6. 書かれていないことの扱い

依存の強さと、崩れる条件の境目は、元の文書に書かれていないことが多い。

### 依存の強さ

| 場合 | 強さ |
| --- | --- |
| 選んだ案の理由が1つしか無い | `critical`。その理由が無ければ判断に根拠が残らないため、モデルの出力にかかわらず固定する |
| 文書が「これが変わったら見直す」と書いている | `critical` |
| それ以外 | `contributing` |

推測で `critical` にはしない。誤って `critical` にすると、崩れても影響の無い前提で見直しを促すことになり、促しが信用されなくなる。

### 崩れる条件

前提の反対がはっきりしていれば書く（「X に機能 Y が無い」なら「X に機能 Y が出た」）。数量の境目（何件を超えたら、何秒を超えたら）は、文書に書かれていなければ空にする。境目は利用者が決めるもので、モデルが作った数字は根拠にならない。

### 利用者への質問

抽出のときに、本人にしか答えられない質問を文書1本につき2件まで溜める。溜めるのは次の2種類とする。

- 既存の記録と食い違う内容があるとき、どちらが今の状況か
- 判断の根拠になっている計測値について、見直す境目

「どの前提が崩れたら決め直すか」は溜めない。理由を複数並べた判断のほとんどが対象になり、まとめて答えられる量にならない。この質問は、前提が実際に崩れて「根拠が減った判断」として挙がった時点で、その判断についてだけ聞く。

## 7. 重複の避け方

抽出するモデルに、次の記録の ID と本文を渡す。

- 同じリポジトリの前提と判断
- どのリポジトリでも通用する前提

同じ中身の記録があれば、新しく作らずにその ID を参照させる。ID は中身を表す短い名前なので、モデルは一覧から同じ中身のものを見つけやすい。

同じ判断がメモリと意思決定ドキュメントの両方に書かれていることがある。先に読んだほうが記録になり、後で読むほうはそれを参照する。

複数の文書を並行して読むと、互いの結果が見えず、同じ前提が別の ID で2件できることがある。見つけたら、統合のイベントで1件にまとめる。

同じ文書の中で、後ろに書かれた判断に前の判断が依存することがある。文書1本の判断は、依存される側を先に並べてから検証する。

---

## 8. モデルと検証

抽出には小さいモデルを使う。文書は1本ずつ読ませ、決まった形（JSON Schema）で出力させる。整理された文書から判断と理由を抜き出す作業は、小さいモデルで足りる。件数が多いので、費用と時間を抑えるほうを優先する。

出力は、記録の形の検証（ID の形、依存先があること、却下した案の名前が合うこと）に文書1本ぶんまとめて通す。1件でも通らなければ、誤りの内容を添えて1回だけ出し直させる。それでも通らない文書は取り込まず、失敗として報告する。一部だけを取り込むと、依存先の欠けた判断が残るためである。

抽出するモデルには道具を持たせない。読むのは渡した文書だけで、ファイルや外部には触れない。

---

## 9. 残っていること

- **会話の履歴からの抽出。** 利用者の発言と直前の返答を対にして読ませる方法、メモリに残った元のセッションから開く方法を、試してから決める
- **経験則の扱い。** 「後から作り替えるほうが高くつく」のような前提は、今は見込み（`expectation`）に入れている。収まらない例が増えたら種類を見直す
- **判断から生まれた制約。** 判断の後で分かった制約は次の判断の前提になるが、元の判断とはつながらない
- **重複の検出。** 別の ID で2件できた前提を、機械的に見つける方法
