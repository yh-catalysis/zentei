## 1. このドキュメントの目的

zentei は、判断ごとに依拠した前提を記録し、前提が崩れたときに、見直しが要る判断を引けるようにするツールである。記録は人が手で書かず、コーディングエージェントとの会話と既存の意思決定ドキュメントから抜き出す。

記録の使い道は、エージェントが作業の初めに関係する前提を読み、崩れた前提に気づいたら知らせることである。記録を溜めること自体は目的にしない。

このドキュメントは、その記録の形（何を1件と数え、何と何をつなぎ、どう保存するか）を決める。抽出の方法、同期の方法、照会のインターフェースは別のドキュメントで決める。

---

## 2. 決定事項サマリ

| 論点 | 決定 |
| --- | --- |
| 記録の単位 | **前提（Premise）・判断（Decision）・予想（Forecast）の3種類**（[§3](#3-3種類の記録)） |
| 前提の書き方 | **1件に事実を1つ書き、何を観測したら崩れたとするかを添える。確かめ方で5種類に分ける**（[§4](#4-前提)） |
| 判断の単位 | **ドキュメントやセッションではなく、決めたこと1つを1件にする**（[§5](#5-判断)） |
| 依存 | **判断から前提または別の判断へ線を引く。線に「役割」と「強さ」を持たせる**（[§6](#6-依存)） |
| 却下した案 | **却下の理由も前提として線を引く。前提が崩れたら、復活しうる案として出す**（[§6](#6-依存)） |
| 見直す条件 | **専用の項目を作らず、「今は成り立っている前提」として持つ**（[§7](#7-見直す条件は前提として持つ)） |
| 予想と確信度 | **期日までに当否が決まる文にする。確信度は本人が述べたものと、モデルが推定したものを分ける**（[§8](#8-予想)） |
| 出どころ | **すべての記録に、誰の発言から、どのモデルが抜き出したかを持たせる**（[§9](#9-保存の形)） |
| 保存 | **追記だけのイベントを、マシン別のファイルに書く。今の状態はイベントから組み立てる**（[§9](#9-保存の形)） |
| 抽出の誤り | **「崩れた」と「抽出が誤りだった」を別のイベントにする**（[§9](#9-保存の形)） |

## 3. 3種類の記録

| 記録 | 中身 | 例 |
| --- | --- | --- |
| 前提 | 判断の根拠にした、確かめられる1つの事柄 | 「サービス A の無料プランには機能 B が無い」 |
| 判断 | 決めたこと1つと、選ばなかった案 | 「機能 B の代わりに、手元のフックで止める」 |
| 予想 | 判断の結果として起きると見込んだ、期日つきの事柄 | 「3か月後も、フックをすり抜けた変更は0件である」 |

前提と予想を分けるのは、見るものが違うためである。前提は「崩れたら判断が覆る」ものとして依存をたどる対象になり、予想は「見込んだとおりになったか」を後から確かめる対象になる。

## 4. 前提

| 項目 | 中身 |
| --- | --- |
| `id` | `pre_` で始まる ID |
| `statement` | 1文。事実を1つだけ書く。数量が分かっていれば数量で書く |
| `breaks_when` | 何を観測したら崩れたとするか。`value` には要らない |
| `kind` | 確かめ方による分類（下の表） |
| `scope` | `global`、またはリポジトリ（`owner/name`） |
| `as_of` | 成り立つことを最後に確かめた日 |
| `evidence` | 根拠（URL、ファイル、計測の方法）。無くてもよい |

状態（`holds`・`broken`・`unverified`）は項目として持たず、確認のイベント（[§9](#9-保存の形)）から決める。

| `kind` | 中身 | 確かめ方 |
| --- | --- | --- |
| `fact` | 外の世界の事実（製品の仕様、料金、制度） | 公開情報を調べ直す。エージェントが自分でできる |
| `measurement` | 自分で測った値（件数、時間、費用） | 測り直す |
| `situation` | 自分の側の状況（利用者、体制、予算、使い方） | 本人に聞くしかない |
| `expectation` | 将来の見込み | 時間がたてば決まる |
| `value` | 方針や価値観 | 確かめるものではない。変えたときに記録する |

理由:

- **1件に事実を1つにするのは**、2つを1件に詰めると、片方だけが崩れたときに状態を決められないためである
- **`breaks_when` を持つのは**、「ほとんど無い」「少ない」のような文は、崩れたかどうかを後から誰も決められないためである。`statement` に当時の数量を書き、`breaks_when` に境目を書く。元の記述から境目が読み取れないときは、モデルに作らせず、空のままにして本人に聞く対象にする
- **`kind` を確かめ方で分けるのは**、前提を自動で見直すときに、誰が何をすればよいかが `kind` で決まるためである。`fact` はエージェントが調べ直せるが、`situation` は本人に聞くことになる
- **`scope` に `global` を持つのは**、製品の仕様のような前提が複数のリポジトリの判断で使われるためである。リポジトリごとに別の前提として持つと、崩れたときに一部の判断しか引けない
- **`as_of` を持つのは**、同じ事柄でも時点で真偽が変わるためである。古い `fact` から順に確かめ直せる

## 5. 判断

| 項目 | 中身 |
| --- | --- |
| `id` | `dec_` で始まる ID |
| `scope` | リポジトリ（`owner/name`）、または `global` |
| `title` | 何についての判断か |
| `chosen` | 決めた内容 |
| `alternatives` | 選ばなかった案の一覧。各案に `option`（案）と `reason`（選ばなかった理由の文） |
| `decided_on` | 決めた日 |
| `sources` | 出どころ（セッション、ドキュメントの節、Issue、PR） |
| `depends_on` | 依存の一覧（[§6](#6-依存)） |
| `review_on` | 見直す日。無くてもよい |

状態（`active`・`superseded`・`withdrawn`）はイベントから決める。

**1つのドキュメントやセッションを1件にしない。** 意思決定ドキュメントは、1本の中に複数の決定を表で並べ、節ごとに理由を書くことが多い。ドキュメント単位にすると、前提が1つ崩れたときにドキュメント全体が「覆る」と出てしまい、どの決定を見直せばよいか分からない。

---

## 6. 依存

判断の `depends_on` に、次の形の線を並べる。

| 項目 | 中身 |
| --- | --- |
| `on` | 前提の ID、または別の判断の ID |
| `role` | `supports`（選んだ案の根拠）、`rules_out`（ある案を却下した根拠） |
| `alternative` | `role` が `rules_out` のとき、どの案か |
| `strength` | `critical`（崩れたら判断が覆る）、`contributing`（根拠の1つ） |

前提が崩れたとき、線の種類によって出すものを変える。

| 崩れた線 | 判断の扱い |
| --- | --- |
| `supports` かつ `critical` | 見直しが要る。この判断に依存する別の判断も、順にたどって同じ扱いにする |
| `supports` かつ `contributing` | 根拠が減った、と出す。判断は有効なままにする |
| `rules_out` | 却下した案が復活しうる、と出す |

理由:

- **判断から判断へも線を引くのは**、「AI を1社に絞る」という判断の上に「ローカルのモデルは使わない」が乗るように、判断が別の判断の前提になるためである
- **却下の理由にも線を引くのは**、「機能が無いので見送った」案は、その機能が出たときに選び直す価値があるためである。選んだ案の根拠だけを追うと、これを拾えない
- **強さを分けるのは**、理由を5つ並べた判断で1つが崩れるたびに「覆る」と出すと、通知が多すぎて読まれなくなるためである

## 7. 見直す条件は前提として持つ

意思決定ドキュメントには「〜になったら見直す」という条件がよく書かれる。日付で書かれることは少ない。

**この条件は、専用の項目にせず、「今は成り立っている前提」に直して `critical` の線を引く。**

| ドキュメントの記述 | `statement` | `breaks_when` | `kind` |
| --- | --- | --- | --- |
| 「数式の多い文書を扱うようになったら見直す」（別の箇所に「手元の3冊で数式は5個」） | 「手元の文書3冊で、数式は合わせて5個である」 | 境目が書かれていないので空。本人に聞く | `measurement` |
| 「同時に使う人が増えたら構成を分ける」 | 「同時に使う人は1人である」 | 「同時に使う人が2人以上になった」 | `situation` |

1行目のように、元の記述が「多い」「増えた」としか言っていないことがある。境目をモデルが決めると、本人の考えていない基準で「崩れた」と出るので、決めない。

こうすると、見直す条件を満たしたことと、前提が崩れたことが同じ1つの操作（前提を `broken` にする）になる。日付で決めた見直しだけを `review_on` に持つ。

## 8. 予想

| 項目 | 中身 |
| --- | --- |
| `id` | `fct_` で始まる ID |
| `decision` | どの判断についての予想か |
| `statement` | 期日に「はい」「いいえ」で答えられる文 |
| `confidence` | 当たる確率（0〜1） |
| `confidence_source` | `stated`（本人が数字や言葉で述べた）、`inferred`（抽出したモデルが推定した） |
| `due` | 当否を確かめる日 |

結果（`yes`・`no`・`void`）は、確定のイベントで持つ。`void` は、判断を取りやめたなどで当否を問えなくなったものである。

理由:

予想を記録する目的は、確信度と結果のずれを知ることである。「8割」と見込んだことが実際には6割しか起きていないと分かれば、次に「8割」と思ったときに、余裕を多めに取る、先に小さく確かめる、といった手を打てる。人やモデルに点を付けるためのものではない。

理由:

- **確信度の出所を分けるのは**、本人が述べた確信度とモデルが推定した確信度では、ずれの意味が違うためである。前者は本人の見込みの癖を、後者はモデルの読み取りの癖を表す。混ぜると、どちらの癖も分からなくなる
- **結果は、本人が認めたものだけを集計に入れる。** 何が起きたかを知っているのは本人で、エージェントが会話から読み取った結果は誤ることがある。エージェントは結果の案を出し、本人が認める
- **予想の無い判断を認める。** 意思決定ドキュメントには確信度が書かれないことが多く、既存の記録から取り込んだ判断には、たいてい予想が付かない。これらは依存の照会に使い、ずれの集計には入れない

## 9. 保存の形

**追記だけのイベントを、JSON Lines で `events/<machine>/<YYYY-MM>.jsonl` に書く。** 今の状態は、全マシンのイベントを時刻順に読んで組み立てる。

```json
{"id": "evt_…", "at": "2026-01-15T09:30:00+09:00", "machine": "desktop", "type": "premise.added", "origin": {"kind": "session", "ref": "…", "speaker": "user", "extractor": "…"}, "data": {"id": "pre_…", "statement": "…", "kind": "fact", "scope": "global", "as_of": "2026-01-15"}}
```

| イベント | 中身 |
| --- | --- |
| `premise.added`・`decision.added`・`forecast.added` | 記録を1件足す |
| `premise.checked` | 前提を確かめた結果（`holds`・`broken`）、確かめた日、根拠 |
| `decision.revised` | 判断の項目を書き換える（依存の追加と削除を含む） |
| `decision.closed` | 判断を `superseded`（置き換えた判断の ID つき）または `withdrawn` にする |
| `forecast.resolved` | 予想の結果と、確定した日 |
| `merged` | 重複した2件を1件にまとめる。古い ID への参照は新しい ID に読み替える |
| `retracted` | 抽出の誤りとして、記録を無かったことにする |

理由:

- **追記だけにし、ファイルをマシンで分けるのは**、複数のマシンから Git で同期しても、同じファイルを2か所で書き換えることが起きないためである。記録1件を1ファイルにして書き換える形だと、両方のマシンで同じ記録を直したときに衝突する
- **すべてのイベントに `origin` を持たせるのは**、記録の確かさが出どころで違うためである。`speaker` は、元になった発言が本人のもの（`user`）か、エージェントが言って本人が否定しなかったもの（`assistant`）かを表す。本人が自分の言葉で述べた前提と、エージェントの説明から拾った前提を分けて扱える。`extractor` は抜き出したモデルで、あるモデルの抽出だけをやり直す、集計から外す、といった扱いができる。同じ会話を2回処理したときの重複も、`origin` で見分ける
- **`retracted` を `broken` と分けるのは**、意味が違うためである。`broken` は「当時は正しかったが、今は成り立たない」で、依存する判断の見直しを促す。`retracted` は「そもそも抽出が誤りだった」で、何も促さない。機械で抜き出す以上、誤りを消す道が要る
- **`merged` を持つのは**、同じ前提が別のセッションから違う言い回しで抜き出されるためである。抽出のときに既存の前提を渡して ID で参照させるが、漏れは残るので、後からまとめられるようにする

## 10. 却下した案と理由

| 案 | 却下理由 |
| --- | --- |
| ドキュメント1本・セッション1回を判断1件にする | 前提が崩れたとき、どの決定を見直すのか分からない（[§5](#5-判断)） |
| 前提を判断の中の文章として持つ（前提に ID を振らない） | 複数の判断が同じ前提に依拠していることを引けない。このツールの中心の機能が成り立たない |
| 見直す条件を、判断の専用の項目にする | 前提が崩れることと同じ事柄を、2つの仕組みで扱うことになる（[§7](#7-見直す条件は前提として持つ)） |
| 予想を前提の一種（`expectation`）にまとめる | 依存をたどる対象と、当否を数える対象が混ざる。確信度と期日は予想にしか要らない（[§3](#3-3種類の記録)） |
| 確信度をすべてモデルに推定させ、区別しない | 本人の見込みの癖と、モデルの読み取りの癖が混ざる（[§8](#8-予想)） |
| 前提の境目（`breaks_when`）を、書かれていないときはモデルに決めさせる | 本人の考えていない基準で「崩れた」と出る（[§7](#7-見直す条件は前提として持つ)） |
| 記録1件を1ファイルにして書き換える | 複数のマシンで同じ記録を直すと衝突する（[§9](#9-保存の形)） |
| SQLite のファイルを同期する | バイナリなので、2台で別々に書くと統合できない。照会を速くするために、イベントから手元で組み立てる分には使ってよい |

---

## 11. 残っていること

- 予想を最初の版に含めるか。結果を本人が認める手間が要り、依存の照会には無くても困らない
- 抽出のときに、既存の前提のうちどれをモデルに渡すか（件数が増えたときの絞り方）
- 2台の時計がずれているときの、イベントの順序の決め方
- `value` の前提を変えたとき、依存する判断をどう出すか
